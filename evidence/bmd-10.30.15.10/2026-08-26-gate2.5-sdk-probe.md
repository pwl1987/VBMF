# Gate 2.5 (path A) — DeckLink SDK 运行时可达性 实机实测

**日期:** 2026-08-26
**主机:** BMD `10.30.15.10`(runc)
**目的:** 验证 `libDeckLinkAPI.so` 在目标运行环境(尤其 Option B runc 容器)可达,
为 Gate 6/7 (GStreamer pipeline / 信号 / 深度枚举) 铺路。

---

## 关键实测事实

`/usr/lib/libDeckLinkAPI.so` 在 BMD 宿主机**已存在**(驱动安装自带, 8.8MB)。
`nm -D` 显示它**不导出纯 C 的 `GetDeckLinkAPIVersion`**, 而是 C++ COM 工厂函数:
```
CreateDeckLinkAPIInformationInstance_0001
CreateDeckLinkIteratorInstance_0004
CreateDeckLinkDiscoveryInstance_0003
... (IDeckLink* C++ vtable 类型信息)
```
→ 初期的 `GetDeckLinkAPIVersion` probe 误报 `undefined symbol`。修正为校验收到的
`CreateDeckLinkAPIInformationInstance_0001` + `CreateDeckLinkIteratorInstance_0004`,
符号存在即证明 SDK 运行时与 ABI 可见。

## 三场景验证 (media-agent + libloading dlopen)

| 场景 | 命令要点 | 结果 |
|---|---|---|
| 宿主机 | `~/media-agent`(默认搜 `/usr/lib`) | ✅ `SDK libDeckLinkAPI.so reachable, entry symbols present` |
| 容器 Option B **无挂库** | `docker run ... --cap-drop=ALL ... -v media-agent:ro` | ❌ `load failed: cannot open shared object file` |
| 容器 Option B **bind-mount 库** | 加 `-v /usr/lib/libDeckLinkAPI.so:/usr/lib/libDeckLinkAPI.so:ro` | ✅ `entry symbols present` |

## 结论

1. **SDK 运行时在 BMD 宿主机默认可达**(系统库路径已含)。
2. **Option B 容器默认不含宿主库** —— 必须与 discovery 同等的显式挂载
   (`-v /usr/lib/libDeckLinkAPI.so:...`)才能让 Rust FFI 加载。这印证了
   Gate 6/7 的部署形态: `compose.acceptance.yml` 的 media-agent 服务需
   把 SDK .so 挂进容器(或用含 SDK 的定制镜像), 否则深度枚举/采集无法启动。
3. **FFI 集成前提已验证**: `libloading::Library::new("libDeckLinkAPI.so")` 在
   Option B 容器内可行; 真正的版本/设备枚举经 C++ vtable (IDeckLink*),
   留 Gate 6/7 用 bindgen 生成安全 Rust 包装后实现。
