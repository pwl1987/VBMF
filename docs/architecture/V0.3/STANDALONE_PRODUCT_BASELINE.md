# VBMF V0.3 独立运行产品基线

> **状态：实施基线**  
> **版本：V0.3**  
> **定位：VBMF 独立运行、Web 操作及后续母框架集成的产品边界与实施验收基线**

## 1. 目的

V0.3 要把 VBMF 从 V0.2 运行时基线推进为可以独立启动、独立操作、独立验收，同时能够在未来无语义分叉地接入母框架的专业实时媒体播出系统。

VBMF 不等待母框架完成后才可使用。

两种运行形态：

```text
独立模式：浏览器 → VBMF Web 控制台 → 控制接口 → VBMF 运行时 → 适配器 / 硬件

集成模式：上层平台 → VBMF 集成边界 → VBMF 运行时 → 适配器 / 硬件
```

两种模式必须共享同一套领域、运行时、命令、查询、事件、健康和执行语义，不得维护两套运行时业务逻辑。

## 2. 产品所有权边界

VBMF 的规范所有权包括：

- 广播会话与运行时执行；
- 信号、源、端口及运行时状态；
- 媒体管线执行；
- 切换、故障切换与冗余；
- 运行时所需的时钟、同步和媒体语义；
- 运行时健康、看门狗与恢复；
- 硬件和厂商适配器边界；
- 运行时控制、查询和事件接口。

VBMF 不拥有：

- 母框架本身；
- 企业统一平台；
- CMS/MAM 业务事实数据库；
- 新闻业务事实；
- AI/知识事实；
- 全局身份、组织和权限事实；
- 全局搜索、通知和任务中心；
- 通用媒体 SDK 事实。

## 3. 独立模式是一等产品模式

独立模式不是开发调试模式，正式用于：

1. 单机和局域网测试；
2. 工程部署；
3. 广播运行时独立运行；
4. 无母框架环境下验收；
5. 故障诊断和运维。

最小组成：

```text
VBMF
├── Web 控制台
├── 控制接口
├── 本地配置
├── 运行时查询
├── 命令分发
├── 事件投影
├── 健康 / 诊断
└── 广播运行时
    ├── GStreamer
    ├── FFmpeg
    ├── DeckLink
    └── 操作系统 / 网络
```

独立启动不得强制要求母框架、业务平台、直播平台、新闻系统或 AI 平台在线。

## 4. Web 控制台范围

V0.3 需要形成真正可操作的产品入口，但必须区分“P1 控制台骨架”和后续专业操作控制台。

### P1 控制台骨架

只要求：

- 运行时首页；
- 健康状态；
- 设备/源基础观察；
- 会话基础观察；
- 核心命令入口；
- 事件/诊断基础观察；
- 工程信息。

### 后续专业控制台

在 P2/P4 逐步增加：

- Dashboard；
- Sources；
- Sessions；
- Switcher；
- Outputs；
- Recording；
- Health；
- Incidents；
- Engineering；
- Graph/Preflight；
- AVSync/Latency；
- Redundancy。

这样避免把完整专业控制台错误地塞进 P1。

### 界面边界

浏览器只能通过控制、查询和事件边界工作：

```text
浏览器 → 控制接口 → 命令 / 查询 / 事件 → 运行时
```

禁止浏览器直接调用 GStreamer、FFmpeg 命令行、DeckLink SDK、Rust 内部对象或内部存储。

## 5. 集成模式

接入母框架时，上层平台可以提供或替换：

```text
身份提供者
注册提供者
认证提供者
策略提供者
```

但不能改变：

```text
领域语义
运行时执行
命令语义
查询语义
事件语义
```

平台不得绕过 VBMF 集成边界直接操作厂商适配器。

## 6. 六类边界

新增能力必须首先判断属于：

1. 核心/跨领域契约；
2. 契约/模式；
3. 软件开发工具包/开发者消费；
4. 控制/接口；
5. 广播运行时/领域；
6. 基础设施/厂商适配器。

属于业务、应用、体验或全局平台的能力，默认不进入 VBMF 核心。

## 7. 共享软件开发工具包

通用 SDK 只沉淀已经稳定并被真实消费者证明过的契约。候选包括：标识、上下文、版本、生命周期、错误、事件、命令、幂等、来源追踪和可观测性。

`vbmf-sdk` 只表达广播运行时专业契约，例如广播会话、信号源、信号图、切换/故障切换、时钟域、健康树、运行时能力、设备/端口、延迟/音视频同步。

SDK 不得成为 VBMF 内部 Rust 接口的镜像，也不得暴露 GStreamer、FFmpeg、厂商 SDK 或数据库内部对象。

## 8. V0.2 兼容原则

V0.3 是扩展，不是修改 V0.2 冻结语义的许可。除非建立新的版本化契约并提供迁移证据，否则以下语义必须保持兼容：

- Runtime Domain 语义；
- Canonical 媒体语义；
- Runtime State 语义；
- Command Contract 语义；
- Idempotency 三平面分离；
- Error Classification、CommandStatus、IdempotentDispatch 的分离；
- Event Projection 语义；
- 外部接口边界；
- Transport 边界；
- Health 不变量；
- V0.2 既有架构红线。

发现真实缺陷时优先修实现；若确实必须改变冻结语义，必须走版本化契约流程。

## 9. V0.3 红线

### 红线一：运行时是唯一执行事实源

不能建立第二套运行时、模拟运行时或 UI 专用执行路径。控制台、测试 Gate 和适配器最终都必须进入正式运行时。

### 红线二：观测不等于配置

观测不得偷偷写回图、后端或业务配置形成隐式决策。

### 红线三：语义意图不等于执行计划

意图到执行计划的转换必须发生在明确的运行时/编排层。

### 红线四：标准模型不等于厂商模型

标准类型不得包含厂商字段，不得直接依赖 GStreamer、FFmpeg 或 DeckLink 实现。

### 红线五：界面不得越权

UI 不能绕过控制接口直接控制运行时、适配器或存储。

### 红线六：命令、幂等、错误三平面分离

不得把命令状态、幂等结果和错误分类合并为一个状态字段。

### 红线七：事件单向投影

运行时事件必须经过明确投影/输出边界，业务系统不得反向改写运行时事实。

### 红线八：单一事实所有者

VBMF 只拥有广播运行时事实；业务内容、AI、用户、组织、全局资产等必须由各自事实所有者持有。

### 红线九：独立模式与集成模式不得分叉运行时

两种模式可以更换控制、身份和注册提供者，但不能出现两套运行时实现。

### 红线十：不能因为方便就抽共享模块

共享必须有稳定契约、明确所有者、真实消费者、兼容性和退出路径。

### 红线十一：厂商适配器必须可替换

GStreamer、FFmpeg、DeckLink 等必须位于适配器/基础设施边界内。

### 红线十二：不为未来提前制造复杂基础设施

没有真实需求时，不提前引入微前端、分布式控制面、服务网格、复杂事件总线或大型共享服务。

## 10. 不可变项

V0.3 实施期间以下内容视为不可变基线：

1. VBMF 的规范角色是广播运行时/媒体织构；
2. 运行时是唯一执行事实源；
3. 独立模式必须可以独立启动和 Web 操作；
4. 独立与集成共用运行时；
5. 浏览器必须经过控制接口；
6. 标准层与厂商适配器隔离；
7. 观测、意图和执行不得偷换；
8. 命令、幂等和错误三平面分离；
9. 事件经过明确投影/输出边界；
10. 不建立业务内容、AI、用户、全局资产等第二事实源；
11. V0.2 冻结契约未经版本化流程不得偷偷修改；
12. 新功能必须经过所有权和边界审查；
13. 生产 Gate 必须使用正式运行时；
14. 新增长期共享模块必须满足母架构共享模块准入条件。

## 11. 可以变化的内容

在不触碰红线的情况下可以演进：

- Web UI 框架与组件实现；
- 页面数量和布局；
- 独立模式配置文件格式；
- Transport 实现细节；
- Storage 实现细节；
- Adapter 内部实现；
- Runtime 内部模块拆分；
- 日志和指标采集实现；
- CLI；
- 开发测试辅助工具；
- 新的广播能力。

## 12. 新功能与缺陷处理流程

新增功能：

```text
需求
 ↓
所有权判断
 ↓
边界分类
 ↓
契约影响分析
 ↓
V0.2/V0.3 兼容性分析
 ↓
Runtime 复用点分析
 ↓
实现
 ↓
单元 / 集成 / 真实 Runtime Gate
 ↓
Standalone Web 验证
 ↓
一致性证据
```

缺陷：

```text
真实 Bug
 ↓
定位事实来源
 ↓
最小修复
 ↓
回归测试
 ↓
真实 Runtime 验证
 ↓
继续新增功能
```

不得通过 UI 特殊分支或旁路 Runtime 掩盖缺陷。

## 13. V0.3 实施阶段

### P0：基线冻结

整理 V0.3 设计包、映射 V0.2 冻结项、形成保留/迁移/抽取/替换/禁止清单。

### P1：独立产品骨架

- 独立启动；
- 本地配置；
- 控制接口；
- 查询接口；
- 事件投影；
- Web 控制台骨架；
- 运行时生命周期；
- 正式运行时控制面接线。

P1 **不**实现全部 V0.3 接口命名空间，不引入完整命令新契约，不引入 SSE/WebSocket，不建设调度、资源放置、集群高可用等后续领域。

### P2：专业操作控制台

Dashboard、Sources、Sessions、Switcher、Outputs、Health、Engineering 等。

### P3：缺陷与运行时加固

回归、故障注入、24 小时稳定性、观察器、看门狗和恢复验证。

### P4：广播专业能力

Recording、Incident Timeline、Graph/Preflight、Capability、音视频同步/延迟、冗余等。

### P5：一致性与符合性

母框架契约映射、Standalone Consumer Evidence、SDK 候选稳定性评估。

### P6：母框架集成

平台身份/控制、注册/解析和统一界面集成，但不改变运行时核心。

## 14. P1 独立控制闭环 Gate

P1 必须证明运行时真正活起来，而不是只证明 HTTP 能返回 200：

```text
进程启动
 ↓
Standalone Boot
 ↓
Runtime READY
 ↓
GET /health
 ↓
GET /api/v1/runtime
 ↓
POST /api/v1/commands
 ↓
命令接受 / 执行
 ↓
运行时状态发生变化
 ↓
再次 GET runtime
 ↓
GET event projection
 ↓
出现对应事件
 ↓
相同幂等请求重放
 ↓
already_applied
 ↓
正常关闭
```

这是 P1 的核心验收门。

## 15. V0.3 独立 MVP 验收

至少满足：

- 不依赖母框架即可启动；
- 浏览器可以进入控制台；
- 可以读取运行时状态；
- 可以发现/查看设备和源；
- 可以查看并控制会话；
- 可以执行受契约保护的核心命令；
- 可以观察事件和健康状态；
- UI 操作最终进入正式运行时；
- 运行时错误不会被 UI 静默吞掉；
- 核心路径具备回归和集成证据。

## 16. 当前实施裁决

P1 的核心不是“把一百多个接口全部实现”，而是：

> **激活现有运行时和控制面，形成可独立启动、可 Web 操作、可查询、可命令执行、可观察事件并可正常关闭的完整闭环。**

现有 V0.2 已验证的命令、幂等、错误和事件语义优先保持。V0.3 新增专业领域按后续阶段逐步实现。
