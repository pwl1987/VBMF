# VBMF V0.3 — 广播媒体 Runtime 与 API 总体设计

> **状态：已锁定进入详细设计**  
> 日期：2026-09-11  
> Scope: VBMF V0.3 顶层产品、领域、Runtime、API、部署与扩展设计的冻结基线。
>
> 本文件是 **VBMF 仓库内部的产品/架构详细设计 SoT**。母框架 `media-digital-architecture` 只负责跨系统边界、共同语义、契约治理、依赖方向与共享模块准入；不承载本文件中的 Broadcast Runtime 专业实现细节。

---

## 0. 设计决策

VBMF V0.3 顶层产品定位正式冻结为：

> **VBMF = Professional Real-Time Media Playout System**  
> **专业实时媒体播出系统 / Real-Time Media Runtime & Fabric**

VBMF 的第一性任务不是“编码”“转码”“网关”“切换”或“采集”，而是：

> **可靠地完成专业实时媒体从输入、同步、处理、制作、编排、播出、保护、传输到最终输出的完整运行时生命周期。**

因此：

- Encoder / Decoder / Transcoder 是能力；
- Media Gateway 是能力与部署角色；
- Production Switcher 是能力；
- Scheduler 是编排能力；
- Virtual Channel 是播出对象；
- HA / Failover 是连续性能力；
- 5G Contribution 是输入/贡献能力；
- Recording / Replay / Timeshift 是 Runtime 能力；
- Preview / Snapshot / Multiview 是观察与运营能力。

它们共同服务于同一个产品边界：**Real-Time Media Playout**。

# 1. 与母框架的关系

## 1.1 母架构对齐

VBMF 必须继续遵守母框架的专业系统定位：
```text
Media Digital Architecture
        │
        ├── Business / Application
        ├── Intelligence
        ├── Processing Engines
        ├── Live Operations
        │
        └── VBMF
              ↓
       Broadcast Runtime / Fabric
              ↓
        Infrastructure
```

母框架已明确：

- Canonical ownership 中 `Broadcast runtime = VBMF`；
- VBMF 不成为 CMS、业务平台或企业统一平台；
- Runtime 可以独立实现专业能力；
- 跨系统使用版本化 API/Event Contract；
- 底层 Runtime 不反向依赖上层业务实现；
- Shared Module 应遵循 Contract-first + real-consumer evidence。

因此本文件是在母框架的 Runtime 边界内**纵向深化 VBMF**，不是重新定义母框架。

# 8. 分布式 Runtime

VBMF V0.3 从顶层即支持：
```text
All-in-One
Functional Split
Multi-Node
Cluster
Hybrid
```

示例：
```text
Node A: Capture
Node B: Decode
Node C: Processing
Node D: Encode
Node E: Gateway
Node F: Playout Scheduler
```

逻辑 Pipeline 不需要因为重新部署到其他 Node 而改变。

### 不可妥协项

1. Pipeline 不绑定物理 Node。
2. Workload 不等于 OS Process。
3. Node 不固定承担某一种功能。
4. Scheduler 不执行媒体处理。
5. Control Plane 不承载实时 Media Stream。
6. Cross-Node Media 必须通过明确 Transport。
7. 单机与分布式使用同一 Domain Contract。
8. HA / Scheduling 不得产生第二套 Pipeline Model。
9. Capability / Resource / Placement 驱动部署变化。
10. 所有部署模式必须服从 Signal Continuity。

# 21. Command / Intent / Plan / Fact

必须严格区分：
```text
Intent
 ↓
Plan
 ↓
Command
 ↓
Execution
 ↓
Runtime Fact
 ↓
Event / Observation
```

例如：
```text
“切换到 Backup-A”
```

是 Intent。

Runtime 生成：
```text
Prepare Backup-A
Verify readiness
Fence Primary
Switch
Verify Output
```

这是 Execution Plan。

真正发生：
```text
Primary fenced at T1
Backup active at T2
42 frames dropped
```

才是 Runtime Fact。

---

# 22. Observation / Configuration / Policy

必须三分：
```text
Observation
Configuration
Policy
```

Observation：系统实际看到什么。

Configuration：系统应该如何运行。

Policy：遇到条件时允许或要求采取什么行为。

禁止：
```text
Observation
   ↓
偷偷修改 Configuration
   ↓
隐式改变 Runtime
```

所有自动决策必须有明确的 Policy / Decision / Execution 边界。

未来不可预知能力必须通过扩展点进入，而不是无限修改 Core。


```text

labels

```

但扩展不得改变核心 Canonical Semantics。

## 25.2 New Feature Admission Test

任何新功能先判断：
```text
Does it change Core Domain semantics?
        ↓ no
Can it be Capability?
        ↓ no
Can it be Adapter?
        ↓ no
Can it be Protocol?
        ↓ no
Can it be Policy?
        ↓ no
Can it be Workload / Resource?
        ↓ no
Only then consider Core Domain change.
```

这条规则用于防止“新需求 = 新顶层模块”的架构膨胀。

# 30. Runtime Authority Model

VBMF 内部事实层次：
```text

      ↓
Runtime State
      ↓
Runtime Fact
      ↓
Event / Observation / Audit
```

其中：

- Configuration 表达期望；
- Runtime State 表达当前运行状态；
- Runtime Fact 表达已经发生的事实；
- Event 是事实的跨边界投影；
- Observation 是运行观察数据；
- Audit 是责任与证据记录。

任何模块都不得隐式把这些概念合并。

# 33. Master 红线

以下为 V0.3 顶层不可变红线。

### R1 — VBMF 角色

VBMF 是 Broadcast Runtime / Real-Time Media Playout System，不是 CMS、AI 平台、统一企业平台。

### R2 — Runtime 唯一执行权威

所有真实媒体执行最终必须进入 Production Runtime。

### R3 — Standalone 一等公民

母框架不存在、不可用或未完成时，VBMF 仍必须独立运行。

### R4 — 唯一 Runtime

Standalone / Integrated 不得分叉成两套 Runtime。

### R5 — Control Plane / Media Plane 分离

控制不承载实时媒体主链路。

### R6 — Pipeline / Node 分离

Pipeline 不绑定物理 Node。

### R7 — Scheduler / Runtime 分离

Scheduler 决定“何时/哪里/分配什么”，Runtime 决定“如何执行媒体”。

### R8 — Canonical / Vendor 分离

Canonical 类型不得被 GStreamer / FFmpeg / BMD / Vendor SDK 污染。

### R9 — Observation / Configuration 分离

观察结果不得隐式成为配置。

### R10 — Intent / Plan / Execution 分离

语义意图不得伪装成执行计划。

### R11 — Command / Idempotency / Error 分离

三者保持独立语义。

### R12 — Event 即事实投影

Event 表达事实，不能成为隐藏 Command 通道。

### R13 — 单一 Canonical Owner

VBMF 只拥有 Runtime 事实，不拥有上层业务事实。

### R14 — 不设第二 Asset Truth

Asset / Content 业务事实由上层 owner 持有，VBMF 只维护 Runtime view / readiness / execution state。

### R15 — Make-Before-Break

可预备的故障切换不得默认采用先停后启。

### R16 — 新功能必须优先使用 Extension Points

新增能力先考虑 Capability / Adapter / Protocol / Policy / Workload / Resource。

### R17 — 不提前引入分布式基础设施

没有真实需求或证据时，不提前引入复杂 Service Mesh、微前端、中央 Event Bus、Universal Shared Service 等基础设施。

### R18 — 核心无厂商锁定

厂商实现可替换。

# 40. 最终架构声明

> **VBMF 是一个专业实时媒体播出系统。**
>
> 它以 Real-Time Media Playout 为核心使命，通过统一的 Media Runtime、Media Graph、Synchronization、Production、Playout、Protection、Transport、Resource、HA 与 Observability 体系，完成从实时媒体输入到最终播出的完整运行时生命周期。
>
> VBMF 可以单机运行，也可以按能力、资源和 Workload 分布到多节点；可以接入多种硬件、协议和移动贡献设备；可以具备软件导播、虚拟频道、延时播出、备份、故障切换和集群能力；但这些都服从同一个 Runtime Domain，而不是形成互相竞争的子产品架构。
>
> **顶层产品边界到此冻结。后续开发从这里向下倒推，不再从功能清单反向定义产品。**
