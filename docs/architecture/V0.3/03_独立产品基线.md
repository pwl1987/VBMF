# VBMF V0.3 — Standalone 产品基线

> 状态：**PROPOSED / BASELINE FOR IMPLEMENTATION**  
> 日期：2026-09-11  
> 范围：将 VBMF 从 V0.2 Runtime 基线推进为“可独立运行、可 Web 操作、未来可无痛接入母框架”的专业 Broadcast Runtime/Fabric 产品。

## 1. 目的

VBMF 不等待 `media-digital-architecture` 完成后才可使用。

从 V0.3 开始，VBMF 必须同时支持两种运行形态：
```text
Standalone Mode
  Browser → VBMF Web Console → VBMF Control API → VBMF Runtime → Adapters/Hardware

Integrated Mode
  media-digital-platform / Control Plane → VBMF Integration Boundary → VBMF Runtime → Adapters/Hardware
```

两种模式必须共享同一套 Domain、Runtime、Command、Query、Event、Health、Execution 语义；不得维护两套业务逻辑。

## 2. 产品定位

**VBMF = Broadcast Runtime / Fabric。**

Canonical 所有权：

- Broadcast session/Runtime 执行
- Signal/Source/Port/Runtime 状态
- Pipeline 执行
- Switch / failover / redundancy
- Runtime 所需的 Clock / timing / media 语义
- Runtime health / watchdog / recovery
- 硬件/厂商 Adapter 边界
- Runtime Control/Query/Event 接口

VBMF 不是：

- 母架构仓库
- 企业级统一平台
- CMS/MAM 事实数据库
- 新闻业务系统
- AI/知识平台
- 全局身份/组织/权限事实源
- 全局搜索、通知、任务中心
- 另一个“Universal Media SDK”

## 3. Standalone Mode 是一等公民

Standalone 不是“开发调试模式”，而是正式产品运行模式，服务于：

1. 单机/局域网内部测试；
2. 工程部署；
3. 广播 Runtime 独立运行；
4. 无母框架环境下的验收；
5. 故障诊断与运维。

最小运行组成：
```text
VBMF
├── Web Console
├── Control API
├── Local Configuration
├── Runtime Query
├── Command Dispatch
├── Event Stream/Projection
├── Health/Diagnostics
└── Broadcast Runtime
    ├── GStreamer
    ├── FFmpeg
    ├── DeckLink
    └── OS/Network
```

启动时不得强制要求 `media-digital-platform`、`news-media-system`、`live-platform`、AI 平台或母框架服务在线。

## 4. Web Console 是 V0.3 的产品入口

V0.3 不再把 Web Console 视为遥远的 Phase 4；先交付一个可工作的 P0 Standalone Console，然后按 Runtime 能力逐步扩展。

### P0 页面

- Dashboard：Runtime、Health、Device、Session、Output、Incident 摘要
- Sources：Source/Device/Port、格式、Signal Lock、Audio、Clock、Readiness
- Sessions：Session 状态、Source、Pipeline、Primary/Backup、生命周期操作
- Switcher：Primary/Backup、Take、Failover、Readiness、Latency、AV Sync
- Outputs：Output 状态、格式、连接性、故障信息
- Recording：录制状态、目标、空间/故障状态、恢复状态
- Health：Health Tree、最近事件、故障归因、恢复动作
- Incidents：Incident Timeline、分类、影响对象、恢复结果
- Engineering：版本、commit、uptime、硬件、adapter、runtime diagnostics、事件流

### UI 边界

Web Console 只能通过 VBMF Control/Query/Event 边界工作。

禁止：
```text
Browser → GStreamer
Browser → FFmpeg shell
Browser → DeckLink SDK
Browser → Rust internal object
Browser → VBMF internal storage
```

正确路径：
```text
Browser → Control API → Command/Query/Event → Runtime
```

## 5. Integrated Mode

未来接入母框架时，平台只替换/增加 Control Plane 能力，不复制 Runtime：
```text
Unified Platform
├── Identity / SSO
├── Global Navigation
├── Workspace
├── Module Registry
└── Platform Control
          ↓
   VBMF Integration Boundary
          ↓
      VBMF Runtime
```

Integrated Mode 不得改变 VBMF Runtime 的核心语义，也不得让平台直接操作 vendor adapter。

## 6. 六类边界

每一个新增能力必须先回答归属：

1. Kernel / Cross-cutting Contract
2. Contract / Schema
3. SDK / Developer Consumption
4. Control / API
5. Broadcast Runtime / Domain
6. Infrastructure / Vendor Adapter

如果属于 Application、Business、Experience 或 Global Platform，则默认不进入 VBMF Core。

## 7. Shared SDK 策略

### 7.1 media-digital-sdk

只承载已经稳定、跨真实 Consumer 证明过的通用 Contract/Reference SDK。第一阶段候选：

- ID
- Context
- Version
- Lifecycle
- Error
- Event
- Command
- Idempotency
- Provenance
- Observability

必须先有稳定 L0 Contract，再形成 L1 SDK；禁止为了“统一”提前建设大型 SDK。

### 7.2 vbmf-sdk

仅表达 Broadcast Runtime 专业契约，例如：

- BroadcastSession
- SignalSource
- SignalGraph
- Switch/Failover
- ClockDomain
- HealthTree
- RuntimeCapability
- Device/Port
- Latency/AVSync

`vbmf-sdk` 不得成为 VBMF 内部 Rust API 的镜像，不得暴露内部实现结构。

## 8. UI 共享策略

未来可建立 `media-digital-ui`，但第一阶段只沉淀稳定的：

- Design Tokens
- Interaction Semantics
- Accessibility
- Global primitives/patterns
- Status/Error/Job/Health 等通用体验语义

VBMF 专业组件进入 `vbmf-ui` 范围，例如：

- SignalGraph
- HealthTree
- Switcher
- BroadcastSession
- ProgramMonitor
- AVSync/Latency
- Failover

禁止把整个 VBMF 专业控制台复制进统一平台 UI 仓库。

## 9. V0.2 LOCK FINAL 的兼容原则

V0.3 是架构扩展，但不是任意修改 V0.2 语义的许可证。

除非明确开立新的版本化 Contract 并完成迁移证据，否则以下 V0.2 已冻结语义必须保持兼容：

- Runtime Domain 语义
- Canonical media 语义
- Runtime State 语义
- Command Contract 语义
- Idempotency 三平面分离
- Error Classification 与 CommandStatus/IdempotentDispatch 的分离
- Event Projection 语义
- External API 边界模型
- Transport 边界模型
- Health 不变量
- 0.7 最高架构红线

发现真实缺陷时：修实现优先；若必须改变冻结语义，走 V0.3+/版本化契约，不在补丁中偷偷改语义。

## 10. 绝对红线（RED LINES）

以下规则任何新增功能都不得违反：

### R1 — Runtime 唯一执行事实源

不能创建第二套 Runtime、模拟 Runtime 或 UI 专用执行路径。Gate/Console/Adapter 都必须最终进入 Production Runtime。

### R2 — Observation ≠ Configuration

观测结果不得偷偷写回 Graph、Backend 或业务配置并形成隐式决策。

### R3 — Semantic Intent ≠ Execution Plan

Intent → Plan → Backend 的转换只能发生在明确的 Runtime/编排层。

### R4 — Canonical ≠ Vendor

Canonical 类型不得包含 vendor-specific 字段，不得依赖 GStreamer/FFmpeg/DeckLink adapter。

### R5 — UI 不得越权

UI 不能绕过 Control API 直接控制 Runtime/Adapter/存储。

### R6 — Command / Idempotency / Error 三平面分离

不得将 CommandStatus、IdempotentDispatch、ErrorClassification 合并成一个“状态字段”。

### R7 — Event 单向投影

Runtime Event 必须经过明确的 projection/sink 边界；业务系统不得反向控制 Runtime Event 事实。

### R8 — 单一 Canonical Owner

VBMF 只拥有 Broadcast Runtime 事实；业务内容、AI、用户、组织、全局资产等事实必须由其他 canonical owner 持有。

### R9 — Standalone 与 Integrated 不得分叉 Runtime

两种模式可以拥有不同 Control/Identity/Registry provider，但不能出现两套 Runtime/Domain/Execution 实现。

### R10 — 不以“方便”为共享理由

代码重复本身不是抽取 Shared Module 的理由。必须有稳定 Contract、明确 owner、真实 Consumer、兼容性与退出路径。

### R11 — Vendor Adapter 必须可替换

GStreamer/FFmpeg/DeckLink 等只能通过 adapter/infrastructure boundary 接入，不得污染 canonical/domain contract。

### R12 — 不为未来架构提前造复杂基础设施

当前没有真实需求时，不提前引入微前端、分布式控制平面、Service Mesh、复杂 Event Bus 或大型 Shared Service。

## 11. 不可变项（NON-NEGOTIABLE）

下列内容在 V0.3 实施期间视为不可变基线：

1. VBMF 的 canonical role：Broadcast Runtime/Fabric；
2. Runtime 是唯一执行事实源；
3. Standalone 必须可独立启动和 Web 操作；
4. Standalone/Integrated 共用 Runtime；
5. Browser 必须经过 Control API；
6. Canonical 层与 vendor adapter 隔离；
7. Observation/Intent/Execution 三者不能偷换；
8. Command/Idempotency/Error 三平面分离；
9. Event 通过明确 projection/sink 边界；
10. 不建立业务内容、AI、用户、全局资产等第二事实源；
11. V0.2 冻结契约未经版本化变更流程不得偷偷修改；
12. 新功能必须经过 ownership/boundary review；
13. 生产 Gate 必须使用 Production Runtime；
14. 任何新增长期共享模块必须满足母架构 Shared Module 的准入条件。

## 12. 可以变化的内容（CHANGEABLE）

在不触碰上述红线的情况下，以下内容允许持续演进：

- Web UI 框架与组件实现；
- 页面数量与布局；
- Standalone 配置文件格式；
- Transport 实现细节；
- Storage 实现细节；
- Adapter 内部实现；
- Runtime 内部模块拆分；
- 日志/metrics 的具体采集实现；
- CLI 工具；
- 开发/测试辅助工具；
- 新的 Broadcast 能力，但必须经过版本与 ownership 审查。

## 13. 新功能准入流程

任何新增功能执行以下顺序：
```text
需求
 ↓
Ownership 判断
 ↓
Boundary 分类
 ↓
Contract 影响分析
 ↓
V0.2/V0.3 兼容性分析
 ↓
Runtime 复用点分析
 ↓
实现
 ↓
Unit / Integration / Real Runtime Gate
 ↓
Standalone Web 验证
 ↓
Conformance Evidence
```

发现 bug 时优先级：
```text
真实 Bug
  ↓
定位事实来源
  ↓
最小修复
  ↓
Regression Test
  ↓
真实 Runtime 验证
  ↓
再继续新增功能
```

不得通过新增 UI workaround、特殊 case 或旁路 Runtime 来掩盖 bug。

## 14. V0.3 实施顺序

### P0 — 基线

- 本文件落盘
- V0.2 冻结项与现有实现逐项映射
- KEEP / MOVE / EXTRACT / REPLACE / FORBID 清单

### P1 — Standalone 产品骨架

- Standalone 启动
- 本地配置
- Control API
- Query API
- Event 流/投影
- Web Console 外壳

### P2 — P0 Broadcast Console

- Dashboard
- Sources
- Sessions
- Switcher
- Outputs
- Health
- Engineering

### P3 — Bug 与 Runtime 加固

- 现有 bug 全量登记
- 回归测试
- 故障注入
- 24h 稳定性
- Runtime observer/watchdog/recovery 验证

### P4 — Broadcast 专业化

- Recording
- Incident Timeline
- Graph/Preflight
- Capability
- AVSync/Latency
- Redundancy

### P5 — Conformance

- Mother Contract 映射
- Standalone Consumer 证据
- vbmf-sdk 候选稳定性评估
- 仅在真实证据充分后进入 Shared SDK

### P6 — Integrated Mode

- Platform Identity/Control 集成
- Registry/Resolver 集成
- 统一 UI 外壳集成
- 不改变 Runtime 核心。

## 15. 当前优先级

用户当前目标是“先把 VBMF 真正用起来”。因此当前优先级严格为：
```text
可启动
  ↓
可 Web 操作
  ↓
核心 Runtime 真跑
  ↓
发现并修复 Bug
  ↓
稳定性
  ↓
专业能力扩展
  ↓
母框架集成
```

母框架未完成不是 VBMF 开发阻塞条件。

## 16. 验收定义

V0.3 Standalone MVP 至少必须满足：

- 不依赖母框架即可启动；
- 浏览器可进入 Console；
- 可读取 Runtime 状态；
- 可发现/查看设备与 Source；
- 可创建/查看/控制 Session；
- 可执行经过契约保护的核心 Command；
- 可观察 Event/Health/Incident；
- UI 操作最终进入 Production Runtime；
- Runtime 错误不会被 UI 静默吞掉；
- 核心路径有 regression/integration evidence；
- 不能因为 Standalone 实现而创建第二套 Runtime。

## 17. 决策记录

本基线吸收并修正此前 VBMF 内部提出的“母框架对齐式升级”建议：

- **采纳**：Standalone + Integrated 双模式；VBMF = Broadcast Runtime/Fabric；`vbmf-sdk` 专业边界；统一 UI 与专业 UI 分层；Contract-first；Conformance-first。
- **收紧**：`media-digital-sdk` 和 `media-digital-ui` 均不提前做成大而全共享仓；先 Contract、再真实 Consumer、再 SDK/Shared Module。
- **否决**：Universal Media SDK、VBMF 自建业务事实源、浏览器直连 vendor、立即微前端化、为未来母框架提前引入复杂分布式基础设施。
