## V0.1 → V0.2 为什么架构重构

V0.1 在实施过程中暴露了**架构级问题**，不能通过局部修改解决。V0.2 是对 V0.1 问题的系统性重构。

| V0.1 问题 | 严重度 | V0.2 修复 |
|---|---|---|
| **无主备切换** — 单点故障 | 🔴 致命 | Switch Mode 3（PACKET/FRAME/MASTER）+ Hot-Standby 3 |
| **健康监控缺失** — 故障后只能 SSH 查 log | 🔴 致命 | Health Tree（5 层） + 7 Health Invariants + 3 轴状态机 |
| **SDI 抽象错误** — 早期尝试把 SDI 当 COMPRESSED 域 | 🔴 正确性 | 4 Layer × 7 Type；SDI = RAW_VIDEO/RAW_AUDIO |
| **没有 Capability Contract** — 切换时无对齐检查 | 🟠 高 | §3.4 switch_mode_decision_tree + X6 Capability Registry |
| **没有 Change Set / 回滚** — 配置变更不可逆 | 🟠 高 | §1.21 Atomic Apply + X3 Configuration Versioning |
| **没有 Hot-Standby 语义** — 不区分 COLD/WARM/HOT | 🟠 高 | §3.5 hot_standby_levels（Policy/Target，**不**是 Runtime State） |
| **没有 Program Master 概念** — 切换后画面跳变 | 🟠 高 | §3.7 Program Master 三独立 graph |
| **没有 Failure Domain** — 输出挂了会错误地切源 | 🟠 高 | §8.9 Failure Domain Matrix（7 Operational + 2 Diagnostic） |
| **没有 Clock Reference** — PTP 挂了系统不知道 | 🟡 中 | §3.12 Clock Reference + clock_quality 等级 |
| **没有 Latency Probe** — 不知道延迟在哪一阶段 | 🟡 中 | §3.6 Latency Probes 10 = 7 Core + 2 Client + 1 CDN |
| **没有 Composition 分层** — Logo 归属冲突 | 🟡 中 | §3.7.1 Program / Variant 双层（RAW 域） |
| **没有 Incident Timeline** — 故障后无法回溯 | 🟡 中 | X4 Incident Timeline（QC → Switch → Recording → Operator Ack） |
| **没有 AVSync Manager** — 音视频漂移无感知 | 🟡 中 | §3.13 AVSync Manager（Measurement + Offset/Drift Correction + Failure Classification） |

## V0.1 → V0.2 演进关键决策

### 决策 1：从单链路到 12 Engines

V0.1 是一条 pipeline：SDI → ffmpeg → SRS → HLS。
V0.2 把这条 pipeline 拆成 **12 个独立 Engines**（Source / Switcher / Playout / Composition / Audio / Master / Output / Recording / Replay / ...）。

好处：每个 Engine 可独立测试 / 替换 / 复用。

### 决策 2：从 Docker 全栈到 Host + Docker 边界

V0.1 是 Docker Compose 全栈。
V0.2 明确：
- **Host 跑媒体栈**（BMD 驱动、FFmpeg、Media Agent）
- **Docker 跑业务栈**（SRS、PostgreSQL、Valkey、Web）

理由：BMD 驱动在 Docker 内易出问题；Host 跑媒体栈更稳定。

### 决策 3：从 fluent-ffmpeg 到自建 FFmpeg Command Builder

V0.1 用 fluent-ffmpeg。
V0.2 决定**自建 FfmpegCommandBuilder**。

理由：fluent-ffmpeg 不能精确控制 Data Plane 标注 / Capability Contract / Runtime Alignment。

### 决策 4：从无版本控制到 Change Set + Rollback

V0.1 配置变更直接改文件 / DB。
V0.2 引入：
- `config_revisions`（版本表）
- `change_sets`（变更集，DRAFT → VALIDATED → APPLIED → ROLLED_BACK）
- snapshot + prepare + commit 的业务层原子切（**不是** DB 事务）

### 决策 5：从无 SoT 到 SoT 锁定

V0.1 每个模块独立判断状态。
V0.2 明确各 SoT（Single Source of Truth）：
- Channel Health：§3.9 Health Tree Aggregation Policy
- Failure Recovery Action：§8.9 Failure Domain Matrix
- Switch Mode：§3.4 switch_mode_decision_tree
- AVSync Classification：§3.13（**仅**识别，**不**决定 action）
- 部署参考：§3.11 current_host_snapshot（**非** Architecture Fact）

### 决策 6：从 1 角色到 4 角色

V0.1：所有人 = Admin。
V0.2：4 角色矩阵（Operator / Director / Engineer / Admin），见 [`docs/phase-0.5/OPERATOR_WORKFLOW.md`](phase-0.5/OPERATOR_WORKFLOW.md) §1。

## 经验教训（V0.1 → V0.2）

1. **架构级问题不能通过局部修改解决** — 必须升级主版本
2. **早期就锁定 SoT** — 否则后期会出现"两个模块各自计算"的不一致
3. **运行时语义要在第一轮就明确** — Lifecycle / Readiness / Health 三轴
4. **Failure Domain 矩阵是必备** — 否则会出现"输出挂了错误地切源"这类反模式
5. **Capability Contract 是 PACKET 切换的硬门槛** — 没有它主备画面会跳变
6. **配置变更必须可回滚** — 否则一次错误 Apply 会导致整个机房瘫痪
7. **SDI = RAW 不是 COMPRESSED** — 这是 V0.1 最大的认知错误，V0.2 §3.1 锁定
