## ① 真实 PipelineController 构图分析（调用链与数据结构）

### 1.1 物化调用链（生产真实路径, 逐环实锚）

```text
SessionManager::start (session.rs:609-628)
  → 对 materialize 产出的每个 PipelinePlan:
    backend.instantiate(plan)                    [session.rs:614]
      = GStreamerPipelineController::prepare     [controller.rs:82-119]
        → handle = NEXT_PIPELINE_ID++            [controller.rs:85]
        → build_pipeline(plan, handle, bus_tx)   [controller.rs:88 → 246-357]
            → launch = plan.output_launch(&video_src, &audio_src)

```

### 1.2 管线真实拓扑（两种形态, pipeline.rs:264-274 实锚）

**带输出段**（`plan.outputs` 非空——`VBMF_OUTPUT_*` env 配置时;
launch 串 pipeline.rs:205-214）:

```text
{video_src} ! video/x-raw ! tee name=v
  v. ! queue ! appsink name=videosink async=false          ← 分析分支
  v. ! queue ! videoconvert ! openh264enc ! h264parse ! {v_sink}   ← 编码输出
{audio_src} ! audio/x-raw ! tee name=a
  a. ! queue ! appsink name=audiosink async=false
  a. ! queue ! audioconvert ! avenc_aac ! aacparse ! {a_sink} {tail}
```

**纯分析**（无输出段——`VBMF_OUTPUT_*` 未设时 fail-soft; controller.rs:266-271）:

```text
{video_src} ! video/x-raw ! appsink name=videosink async=false
{audio_src} ! audio/x-raw ! appsink name=audiosink async=false
```

⚠ **决定性事实（本次 Gate 核心发现）**: 纯分析形态**没有 tee**——
原始媒体面在 caps 之后直连 appsink 被消费掉。MediaTap 只能挂在 tee 的
request src pad 上 ⇒ **注入前提 = 管线必须是 tee 形态**（即双输入
Program 会话要求输出段物化, 或做动态 tee 插入手术——后者复杂度高,
见 ②3）。

### 1.3 实例/句柄数据结构（controller.rs:32-51 实锚）

```rust
GStreamerPipelineController { instances: Mutex<HashMap<PipelineHandle, GstInstance>> }
GstInstance { pipeline: gstreamer::Pipeline, plan, bus_rx, stop_flag, thread }
```

- **controller 独占持有 GstPipeline 对象引用**——任何运行期操作
  （含 tap 注入）必须经 controller 表, 不存在旁路句柄;
- recover = 锁内取 plan clone → remove+stop 旧实例 → 重建新 pipeline
  （**同 handle 换新对象**, controller.rs:146-187）⇒ **tap 在 recover
  后会消失**（挂在旧对象上）——02 设计必须处理 tap 重挂或 tap 随
  recover 重建;
- stop = remove + GstInstance::stop()（stop_flag → join 线程 → Null）
  + HEALTH_ARCS.remove（controller.rs:202-219）。

## ② Media Tap 注入位置（实际代码落点）

### 2.1 首选方案（用户已排序 🟢）: Controller 暴露通用 MediaTap 能力

**语义边界（硬约束, 第四轮终裁）**: controller 只知"媒体输出能力"
（`MediaTap`）, 不知 Program/Switch/ExecutionGroup; 通道命名 = 纯设备
标识派生（如 device UUID 短码）, **不含 program/switch 词汇**。

**契约面落点**（平行于 `contracts/switch.rs` 先例, 不动 backend.rs 五方法）:

```text
src/contracts/media_tap.rs   （新, 执行面契约; 零 Program 语义）
  trait MediaTapPort {
    attach_media_tap(&self, handle, req: MediaTapRequest) -> Result<(), TapError>
    detach_media_tap(&self, handle, req)
  }
  MediaTapRequest { channel: String /*设备标识*/, planes: video|audio|both }
```

**实现落点**（GStreamerPipelineController impl MediaTapPort）:

```text
instances.lock → get(handle).pipeline
  → by_name("v") / by_name("a")            ← parse::launch 命名 tee（§1.2）
  → tee.request_pad_simple("src_%u")
  → ElementFactory("intervideosink"/"interaudiosink").channel=req.channel
  → pipeline.add(el) + el.sync_state_with_parent() + link(tee_pad, el_sink)
```

GStreamer 动态加元素 + sync_state_with_parent 是官方动态管线模式,
PLAYING 态可注入; Program pipeline 端以 `intervideosrc channel=同值`
消费（switch_graph.rs 拓扑替换: 双测试源 → 双 intervideosrc, selector
及其后完全复用 01 已验证结构）。

**消费侧组合**（Program Execution 层, 边界保持）:

```text
bin 组合根: mgr.status(sid).inputs → 每输入 attach_media_tap(device 标识)
  → GStreamerSwitchAdapter.build_program_graph(group)   ← 消费两个 tap
  （adapter 内部按 device→channel 映射建 intervideosrc×2; Pipeline 侧零 Program 知识）
```

### 2.2 次选 🟡: 动态向既有管线插入 tee（纯分析形态兜底）

对无 tee 管线做运行期手术（block caps→appsink pad → 插 tee → 重接）。
复杂度/风险高（pad blocking + 状态同步）, 仅在"Program 会话不允许带
输出段"被裁为硬需求时才研究; **默认不采**。

### 2.3 其余两项维持终裁排序: appsink→appsrc Rust 桥 🔴不推荐 /
Program 直接开双设备 🔴禁止（双采违反排他不变量）。

### 2.4 真实约束清单（02 编码前必须裁）

| # | 约束 | 实锚 | 影响 |
|---|---|---|---|
| C1 | 纯分析管线无 tee | controller.rs:266-271 | Program 会话须带输出段物化（`VBMF_OUTPUT_*` env）, 或裁 §2.2 |
| C2 | recover 重建管线丢 tap | controller.rs:146-187 | tap 生命周期须挂 recover 钩（重挂）或 Program 层检测重挂 |
| C3 | inter 通道音视频同名对 | intervideosink/interaudiosrc 机制 | channel 命名须区分 video/audio 平面（如 `{dev}-v`/`{dev}-a`） |
| C4 | DeckLink 双卡 clock 差异 | 盒 SDI 分钟级抖动（先例账） | L5 Program Timeline 的真实输入差异源, 02 观察项 |

## ⑤ Audio topology（现状 = selector-style, 非 mixer——实码澄清）

**01 真实实现（switch_graph.rs）**: video 与 audio 两平面**均为
`input-selector`**（"program-video-selector"/"program-audio-selector"）,
切换 = 双 selector 同目标 active-pad + 单 av_epoch——即
**selector-style switching with explicit active-source semantics**,
**不是 audiomixer**（probe 报告"audiomixer 在"仅为盒上元素能力清点,
从未被采用）。第四轮终裁"若只是 audiomixer 无 active 语义不给 PASS"
的担忧在现实现中不成立: `ProgramObservation.video_active/audio_active`
分平面回读 + fold 的 `av_paired` 校验即 active-source semantics 的
观测面。02 维持 selector-style; mixer/ducking 属后续产品需求另行裁。

## ⑥ Program Timeline——时间戳在哪里应被重定义/归一化（仅调查, 不实现）

### 6.1 真实 PTS 路径（01 已实证）

```text
源（is-live → pipeline running-time 时基）
  → input-selector 透传（不重打; 每次切换发新 segment event）
  → queue → appsink 观测（buf.pts()）
```

回切 B→A 时两源同 clock 相位差 <1 帧 → 后跳 → 三态机 NonMonotonic
（sticky）——**source timeline ≠ program timeline 的实测证据**。

### 6.2 归一化候选点（真实 GStreamer 机制映射, 四方案不冻结）

| 方案 | 机制 | 落点 | 现实代价/前置 |
|---|---|---|---|
| A 切后 Regenerator | appsink→appsrc Rust 重打（或自定义 element） | selector 之后 | 引入用户空间拷贝+时序; 近似 2.3 被排方案, 除非无替代 |
| B Program Clock/Segment | 下游忽略上游 segment, 以 program clock 重发 | selector 后首元素 | 无现成通用 element; 需自定义/组合 |
| C 出口 normalization | 编码/mux 出口时间戳由 muxer 按输出 clock 生成 | program 编码出口（02 接 openh264enc+flvmux/hlssink2 后） | **交付面 PTS 可能天然连续**——但观测面（appsink）仍透传; 需 02 实测定"哪个 PTS 才是验收对象" |
| D 切换时新 timebase | pad offset（`set_offset`）在切换时刻补差 | Program 层持 selector pad, switch() 内计算 offset | GStreamer 真机制（webrtc 类先用）; 需知两源 PTS 差——观测面可提供 |

### 6.3 02 的 Timeline 工作定义（观察项, 非实现）

02 真机实验须同时记录**观测面 PTS**（appsink, 现有）与**交付面 PTS**
（若接输出段）两列数据, 以数据裁决 C 是否天然满足; A/B/D 在 04 裁。
**本轮不选型、不编码。**
